# 需求澄清门禁 — WiFi PHY 项目证据

**Why**: WiFi PHY RX 链路重构项目中，需求模糊导致的返工成本远超澄清成本。
不澄清就写代码 → 假设填充 → 实现偏差 → 数小时调试 → 信任崩溃。
这个门禁是对这些教训的泛化，适用于任何项目（不限于 FPGA）。

**How to apply**: 每次收到新需求时，按 `rules/15-requirements-gate.md` 的六维框架逐一澄清，
每个维度必须得到明确回答或记录为待验证假设。未完成 → 不动代码。

## 10 条泛化教训（从 WiFi PHY → 任何项目）

### 教训 1: Golden Model 是唯一真相源
**WiFi 实例**: Viterbi 模块在没有与 MATLAB GM 对齐之前就开始写 RTL → 输出 23142 bytes（正确应为 ~2571）。
**泛化**: 任何有参考实现（Golden Model / 参考脚本 / 标准算法）的项目，必须先跑通参考实现并提取测试向量，再写目标代码。
**映射 D3（成功标准）**: 没有可执行的地面真相 → 验证是盲的。

### 教训 2: Pipeline 阶段不可跳过
**WiFi 实例**: 跳过定点量化阶段 → DSP48 估算是"经验猜测" → 资源规划不可信。
**泛化**: 任何多步骤工程流程，前一步骤的输出是后一步骤的输入。估算不能替代实测。流程越严格，质量越高。
**映射 D4（算法路径）**: 处理步骤缺失 → 后续决策建立在沙滩上。

### 教训 3: 文件变体不是版本控制
**WiFi 实例**: freq_recovery 模块产生了 21 个检查版本、coarse_timing TB 产生了 8 个版本 → 130 个垃圾文件 → 不知道哪个是对的。
**泛化**: 代码修改必须在原地完成。创建变体文件是逃避"我不确定怎么改"的表现——根因是需求没澄清。
**映射 D1（范围与边界）**: 不确定"正确行为" → 用多版本试探 → 代码库不可维护。

### 教训 4: 验证是功能的，不是语法的
**WiFi 实例**: `vlog -lint` 通过就以为验证完成 → 实际功能完全错误（28 次 traceback 而非 14 次）。
**泛化**: 语法检查 ≠ 功能正确。验证必须用真实场景、真实数据、可观测的输出对比。
**映射 D3（成功标准）**: 必须定义可执行的功能验证步骤，不能只靠 lint 过关。

### 教训 5: 跨块信号竞态是最隐蔽的 bug
**WiFi 实例**: Viterbi ACS 块和 TB FSM 块的 `r_reinit` 信号——同一拍清除和读取 → NBA 竞态 → 双倍 traceback。
**泛化**: 任何跨模块/跨进程的信号交互，必须精确到 cycle 的时序契约。不能在"差不多"的层面描述。
**映射 D2（数据契约）**: 信号时序语义不清 → 竞态条件 → 最难调试的 bug。

### 教训 6: 帧/包边界语义偏差会级联放大
**WiFi 实例**: deinterleaver 的 `tlast` 按 symbol 触发而非按 frame → viterbi 把整个帧当成 1 bit → 20608 个错误的 `last=1`。
**泛化**: 任何涉及帧/包/消息边界的协议，边界信号的语义（何时置位、持续几拍、按什么粒度）必须精确约定。
**映射 D2（数据契约）**: 帧边界语义是数据契约中最重要的部分。

### 教训 7: 单 context 超 5 模块 → 质量崩溃
**WiFi 实例**: 35 个模块塞进一个 agent context → 上下文溢出 → 质量跳崖。
**泛化**: 任何需要同时处理多个独立单元的任务，超过 ~5 个必须拆分。人的工作记忆有 Miller's Law (7±2)，AI 也一样。
**映射 D1（范围与边界）**: 模块列表过长 → 拆分策略 → 每个 agent 只负责明确的小范围。

### 教训 8: 指令是绝对约束，不是建议
**WiFi 实例**: 用户说"逐模块验证" → agent 批量改所有模块。用户说"四角色分工" → agent 一人干所有活。
**泛化**: 用户的每一个字都是约束。偏离指令 = 浪费用户时间去检查和纠正。
**映射 D1, D3**: 理解偏差是需求澄清失败最直接的证据。

### 教训 9: 微架构必须在编码前正式化
**WiFi 实例**: Phase 1 只输出接口列表（信号名+方向），没有 FSM 状态图、流水线级数、数据通路位宽 → RTL Agent 自己猜 → 代码不可信。
**泛化**: 在写代码之前，设计文档必须包含：状态机图、数据流图、位宽映射表。没有这些 = 设计不完整。
**映射 D5（微架构）**: 这是一个必须单独澄清的维度。

### 教训 10: 仿真碎片是质量信号
**WiFi 实例**: 61 个 `wlft*` 文件、24 个 `vsim_out*.txt` → 不知道哪次仿真的结果有效。
**泛化**: 工作产物（日志、临时文件、中间结果）的混乱程度 = 流程规范程度。混乱 → 不可信 → 不可维护。
**映射 D3（成功标准）**: 验证结果必须可追溯、可复现、有结构化的证据文件。

## MD Spec Only 场景的特殊教训

WiFi PHY 项目有完整的 MATLAB Golden Model（11 个文件），但即便如此仍出现了上述问题。
**如果没有 Golden Model，只有一份 MD 文档描述方案**，风险会更高：

| 风险 | 具体表现 | 预防措施 |
|:-----|:---------|:---------|
| 模糊词陷阱 | "适当处理" → agent 自己定义"适当" | 模糊词词典 → 必须追问到具体行为 |
| 隐含假设 | "输入是 OFDM 符号" → 频域还是时域？ | 每个名词必须显式化定义 |
| 行为描述不可验证 | "支持背压" → 怎么验证？ | 每个"应该"必须对应一个测试 case |
| 算法步骤缺失 | "然后译码" → 软判决还是硬判决？ | 步骤级拆解，不跳步 |
| 数值范围缺失 | "高速处理" → 多少 MHz？ | 所有数值必须有具体范围 |
| 参考缺失 | 不知道"正确"长什么样 | 最小可验证单元策略：先让子功能跑通 |
