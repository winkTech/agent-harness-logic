# 知识文档臃肿症

关联案例: [[cross-project-experience-ref]] (原 1018 行→180 行)

## 教训

**`cross-project-experience.md`** 原版 **1018 行**，其中包含：
- 完整的 Verilog 模块模板（已存在于 `docs/templates/rtl_module_template.v`）
- 完整的测试平台模板（已存在于 `docs/templates/tb_template.sv`）
- 完整的约束文件模板（通用无特征）
- 完整的仿真运行脚本（过于具体）

这些内容使文档变得 **臃肿不可读**，核心信息（目录结构、命名规范、流程规则）被淹没在代码海中。

## 正确做法

| 原则 | 说明 |
|:-----|:------|
| **引用不复制** | 代码模板 → 指向 `docs/templates/`；设计指南 → 指向 `knowledge/primary/domains/fpga/` |
| **文档管规则** | 知识文档负责：结构、规范、流程、检查清单 |
| **模板管内容** | 模板文件负责：完整的可复制代码、示例 |
| **触发管执行** | 可执行脚本（`init-project.sh`）负责：创建项目、搭建脚手架 |

## 检测标准

一个知识文档是否臃肿：

```
❌ 超过 300 行 + 含完整代码块（无已有文件引用）
✅ 不超过 300 行 + 核心规则 + 引用走读
```

## 应用场景

- 写 `algorithm_spec` 时：写规格逻辑，不要复制全部 RTL 代码
- 写 `report_` 时：写分析结论，不要重复算法描述
- 写指南文档时：写决策模式，不要粘贴完整配置文件
- **任何知识文档**：已有代码/模板 → `docs/templates/` 引用之

**Why**: 文档膨胀后，核心规则被掩盖，新项目时没人读到重点。

**How to apply**: 新建/更新知识文档时先问：
1. 这段代码/模板是否已有文件存储？→ 引用
2. 这段内容读者真的需要全文还是摘要？→ 摘要
3. 这个文档超过 300 行了 → 考虑拆分
