# cp_remove — 已知限制与验证边界（1.1.0）

各条来自实测与设计裁决，非推测。

---

## 1. `i_cfg_n_sym` 配错没有兜底

帧尾由该侧带静态给定（owner 裁定 2026-08-03，与"PLCP 在范围外"一致）。本模块
**不校验**它是否与实际帧长一致：

- 配少 → 截断有效数据，末尾若干符号丢失
- 配多 → 帧尾之后把噪声当符号继续吐给下游

`tb_cp_remove` 覆盖了正确值下的帧尾行为；两侧配错的后果由集成方承担。

## 2. 无反压，且不可停顿

上游 `sync_top` 的 `m_axis_tready` 被忽略（其 signoff 明写"无反压契约，稳态须恒高"），
下游 `fft64_sdf` 亦无 `ready`。本模块因此**不提供 `tready`**，也不得停顿输入。

1.0.0 及之前据此写下一条"M1 硬依赖：`fft64_sdf` 与 `channel_est_top` 之间必须有
弹性缓冲"。**2026-08-04 实链测量推翻了它**（xsim，`cp_remove → fft64_sdf →
channel_est_top`，两帧背靠背，中间置理想无限深 FIFO 观测）：

| 场景 | 反压总拍 | 缓冲峰值占用 |
|---|---|---|
| 真实 M1 链路 | **0** | **1** |
| 对抗：去掉 CP 间隙 | 22 | 23 |

**本模块每符号只占 64 拍、留出 16 拍 CP 空档，这个空档就是下游需要的全部弹性。**
故 M1 配置下不需要弹性缓冲。结论依赖 CP 间隙存在——上游节奏若变，实测上界 23 个
条目（详见 `cbb/fft64_sdf/docs/limitations.md` §4）。**承接点是 `cbb/sb_align` 的
`P_DEPTH`**（调到 32 即可），不必新起件。

另：`sync_top` 的 signoff 写明"弹性由下游 `axis_skid_buffer` 承接"，那是 `sync_top`
自己输出侧的事，与本条无关。

## 3. GI2 不由本模块跳过

长前导的 GI2（32 样点）由 `sync_top` 在上游消化——其 `o_fft_start` 与 T1 首样点
同拍（ADR-003）。若上游换成不满足该契约的实现，本模块会从错误的位置起窗，且
**不会报错**。这个前提是隐含的，集成时须核对。

## 4. `i_fft_start` 帧中途重入的语义

当前实现：仅在 UNSYNC 段响应 `i_fft_start`；帧进行中的脉冲被忽略。需求门禁记录里
曾建议"重新起窗以匹配 sync_top 的复位重入语义"，最终选择忽略，理由是 `sync_top`
本身是单突发（locked 保持到复位），帧中途不会再产生 `fft_start`。**若上游语义改变，
本条须重新裁定。**

## 5. `i_cfg_n_sym` 必须 ≥ 1

**n_sym = 0 时 RTL 仍会吐 1 个数据符号**（实测 192 点 = 3 个符号），而 golden
`rx_cp_window` 在 `n_sym=0` 时只出 2 个 LTS（128 点）。

原因在 FSM 的帧尾判据：`r_sym + 1 >= i_cfg_n_sym` 在 `r_sym=0`、`n_sym=0` 时
要走完一整个 DATA 段才成立。0 个数据符号不是合法的 802.11a 帧（至少有 SIGNAL），
所以定为**接口契约 `n_sym ≥ 1`**，而不是改 FSM——改帧尾语义要走需求门禁。

由 `tb_cp_remove_stability` 的 boundary 段实测并记录。

## 6. 帧间必须至少隔 1 个样点

**零间隔背靠背连帧会整帧丢失下一帧**（实测：gap=0 出 0 点，gap≥1 出 256 点）。

原因同样在时序约定：数据段末点的**下一个**样点才触发 `S_DATA → S_UNSYNC`，
而那一拍 `r_seg` 仍是 `S_DATA`，只有 `S_UNSYNC` 分支消费 `i_fft_start`——零间隔时
`fft_start` 与该拍同拍到达，被吞掉。

逐值测量见 `tb_cp_remove_gap` 与 `docs/frame-gap-measurement.json`。
集成中不会触发（`sync_top` 单突发，帧间必有复位），但契约必须写明。
`tb_cp_remove_stability` 的 stress 段把这个行为**锁住**了：若将来有人改 FSM 让零间隔
也能起窗，那条断言会失败并提示更新本节。

**1.1.0 补充——冲刷段不改变这个 ≥1 拍的下限。** 帧尾冲刷占 64 拍（§7），若冲刷段
也不消费 `i_fft_start`，帧间最小间隔就会被抬到 65 拍。实现时实测到过：冲刷吞掉了
第二帧的起窗脉冲，整帧丢失。故 `S_FLUSH` **也响应 `i_fft_start`**——新帧一来立即
中止冲刷直接起窗（新帧的样点本来就会把上一帧的尾巴挤出 fft64，冲刷已无必要）。
stress 段另有一条断言锁住它：间隔 4 拍（远小于 64）起第二帧，必须完整跑出 256 点。

## 7. 帧尾冲刷：输出比切窗结果多 64 拍零

**1.1.0 起，数满 `i_cfg_n_sym` 个数据符号后，本模块会再自驱吐 64 拍 `o_valid` 高、
数据恒零的样点，然后才回 UNSYNC。** 集成方必须知道输出长度是
`(2 + n_sym) × 64 + 64`，而不是 `(2 + n_sym) × 64`。

**为什么必须有**：下游 `fft64_sdf` 的各级 FIFO 只在有效拍移位，拉低 `valid` 不排空
流水。帧结束后本模块若直接静默，fft64 流水里最后一个真符号就**永远出不来**——
每帧稳定丢一个数据符号。2026-08-04 在 `cp_remove → fft64_sdf → channel_est_top`
实链上实测到（`TAIL_STUCK 64` 样点），需求门禁裁定由本模块负责补。

**为什么是 64 拍**：`cbb/fft64_sdf` 的 `tb_fft64_tail` 双向实测钉定——撤 valid 后
恰好卡住 1 个符号，补 64 拍全部排空。不是推的。

**为什么不会给下游造出假符号**：这 64 拍把最后一个真符号挤出去的同时，自己成为
fft64 流水里新的"卡住的那一个"，永不出现在其输出上。`channel_est_top` 的相位 FSM
是 `P_DATA → P_DATA` 自环、没有帧长概念，任何多出的符号都会产出多余的 H——
所以这一条很要紧，已由链路级 TB 实测确认。

**为什么自驱（不等 `s_axis_tvalid`）**：若冲刷也要靠输入拍推进，"最后一个符号能不能
出来"就取决于上游在帧尾之后还送不送样点——那是隐藏依赖，而"靠上游行为碰巧成立"
正是本功能洞的成因。自驱后该依赖消失。

**冲刷段不消费输入**：期间不取 `ri_data`，不丢弃任何样点；新帧的 `i_fft_start` 会
立即中止冲刷（§6）。

## 8. 验证边界

已证：切窗序列逐样点、帧尾计数、侧带只打一次且落在 T1 首点、UNSYNC 期间静默、
帧中途复位后能重新起窗，对治理 golden 的 **2176 点 bit-true**（G-B-03），
OOC 综合后的时序与资源（G-C-01/02，见 CHANGELOG 0.1.1），
帧中途复位的 **8 个受复位寄存器逐项比对**外加 3 个数据通路寄存器的免复位断言
（G-C-04），以及 boundary / stress / backpressure / regression 四个子结果（G-C-05）。

**未证**：板级验证。

**第二仿真器交叉验证已还清**（1.0.1）：全部判据 TB 在 Vivado xsim 2023.1 上用
**同一份 TB、同一套判据**再跑一遍，结果与 iverilog 一致。复现：给本包的
`run_sim.cjs` 加 `--xsim`。本机 ModelSim 回环 RPC 自 2026-08-01 起故障，那条路仍不通。

对拍长度原为 640 点（10 符号），低于 G-B-03 的 2048 下限——当时记为"若门禁按统一
下限判定需补长向量"。0.1.1 已把数据符号数从 8 提到 32，输出 2176 点，该待办清掉。
