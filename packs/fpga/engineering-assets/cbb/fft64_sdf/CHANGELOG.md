# CHANGELOG — fft64_sdf

## [1.0.2] — 2026-08-04 弹性缓冲风险收敛到具名承接点

文档改动，RTL 未动。§4 里"上游节奏若变化需深度 23 的缓冲"这条风险，此前指向的是
一个假想的将来模块（并附注库内 `axis_skid_buffer` / `stream_elastic_pipeline` 深度
不够）。现在链路里紧接本模块的 `cbb/sb_align` 1.0.0 已落地，它本就带深度可配的
缓冲——风险的承接点由此变成一个**存在的、具名的旋钮**：把 `P_DEPTH` 调到 32 即可，
不必新起件。

## [1.0.1] — 2026-08-04 钉住帧尾冲刷契约 + 实链测量修正 + 第二仿真器交叉验证

### 新增 `tb_fft64_tail`：把帧尾行为和"补多少才够"一起钉死

M1 实链测量发现一个没人记过的功能洞：帧结束后 `cp_remove` 转 UNSYNC 静默，
fft64 再也收不到有效拍——流水里**最后一个数据符号永远出不来**，每帧稳定丢。
`docs/limitations.md` §5 早写了"拉低 `i_valid` 不排空流水"，但整条链路里
**没有任何人负责补这个冲刷**。

新 TB 双向断言：撤 `i_valid` 后**恰好卡住 1 个符号**；补 **64 拍**有效零样点后
**全部排空**。后半条把"补多少才够"变成契约数，集成方不用猜。谁改了流水让它
自排空，测试会失败并提示更新文档。

**冲刷责任方尚未裁定**，待需求门禁；在那之前集成方必须自行补 64 拍。

### 实测修正"必须有弹性缓冲"

同一次实链测量（xsim，两帧背靠背，中间置理想无限深 FIFO）：真实 M1 链路
**反压 0 拍、缓冲峰值占用 1**；去掉 CP 间隙的对抗场景才出现 22 拍反压、
峰值 23。CP 空档就是下游需要的全部弹性。1.0.0 那条"M1 硬依赖"是推断，不是实测。

### 第二仿真器交叉验证还清

8 个判据 TB 在 Vivado xsim 2023.1 上用同一份 TB、同一套判据再跑一遍，全过——
**bit-true 那条 2560 点 0 失配由两个独立仿真器各自确认**。复现加 `--xsim`。

途中 xelab 报"设计内时标不一致"：RTL 不带 `` `timescale ``（综合不需要）而 TB 带，
xsim 为默认参数绑定生成的 `fft64_sdf_default` 就报错。显式 `-timescale 1ns/1ps`
解决——仿真器环境差异，不是 RTL 缺陷。

RTL 一个字节未改。

## [1.0.0] — 2026-08-04 owner 签字，**CERTIFIED**

G-SIGN-01 落定，21 道门全绿，成熟度 `qualification → certified`。

`manifest.signoff.scope` 逐条记了复核过的证据（2560 点 0 失配、41 个复位寄存器、
四个 stability 子结果、WNS +6.323 ns、DSP 10/12……）、正确性锚（golden 1.4.1，
三判据 A/B/C）、以及**接受了哪些限制**。其中两条对复用方最要紧：

1. **`P_DIR=1`（IFFT）没有该方向的 bit-true 对拍**。现有向量是正向的，反向只由
   方向专项 TB 与解析判据覆盖。要把本核回切给 `ofdm_tx_top` 复用，**必须先补
   IFFT 方向的 0 容差对拍**——认证覆盖的是 `P_DIR=0`。
2. **与 `channel_est_top` 之间必须有弹性缓冲**。后者会拉低 `tready` 而本模块不能
   被停。这是 M1 的硬依赖，**当前尚未落地**，签字里明记了这一点。

另外仿真器只有 iverilog 一条路径（本机 ModelSim 回环 RPC 自 2026-08-01 起故障），
无第二仿真器交叉验证；板级未验。都写进签字而不是藏起来。

## [0.1.3] — 2026-08-04 复位/稳定性取证 + 可复现入口，只剩签字

新增两个 TB 与一个复现入口，G-C-04 / G-C-05 / G-GATE-02 全部通过。
**本包现在只卡在 G-SIGN-01（owner 签字）。**

**G-C-04**（`tb_fft64_reset`）：先用 6 个符号把流水灌满（远超 75 拍总延迟），
再拉复位并保持 3 拍，对 **41 个受复位寄存器**逐项比对——core 的 6 个 SDF 级
（`r_cnt`/`r_warm`/`ro_v`）、2 个复乘（`r_cnt`/`r_v1..3`）、75 拍侧带延迟线、
输出级，以及 reorder 的写侧/读侧/输出三段。复位期间输入继续翻转，复位必须压得住。

数据通路与各级 FIFO 按设计**不复位**（利于综合器吸收成 BRAM/SRL 宏），代价是复位后
首符号带未初始化值、必须预热一个符号——这是配套契约不是缺陷。TB 验证了复位释放后
能重新跑出 64 整数倍长度的输出。

**G-C-05**（`tb_fft64_stability`）：

- **boundary —— s21 不回绕的第一份实测证据**。满幅 Q2.14 直流下 bin0 的理论值
  `64x/8 = 8x` 远超 s16，实测**饱和到 +32767 而不是回绕成负数**；满幅 Nyquist
  交替同理落在 bin32。此前"s21 够用"只有解析论证（对抗构造上界 40.71 < 64），
  现在有了满幅工况的直接观测。两例的非目标 bin 均 ≤ 8 LSB。
- **stress** —— 64 个符号连续跑，每符号 `o_idx` 完整覆盖 0..63 且顺序正确、
  `o_sb` 恰 1 次并落在 idx=0。SDF 计数器与重排乒乓无累积漂移。
- **backpressure** —— 本模块无 ready，停顿由 `i_beat`（CE）承担。判据是
  `i_beat` 按 0~3 拍花样拉低时，768 个输出点的 `(re, im, o_idx)` 逐点与
  `i_beat` 恒高的参考跑**完全相同**；冻结期间把输入线换成满幅毒值也未被采样。

**G-GATE-02**：`run_sim.cjs` 跑全部 7 个 TB，`--install` 由实跑结果落证据。
任一 TB 不过即整体失败且不写任何证据。**不含向量重生成**——那是 golden 侧动作，
入口在 `models/comm/ofdm` 的 `run_all_tests`，不该混进 RTL 侧回归。

## [0.1.2] — 2026-08-04 G-B-03 用治理资产复跑通过，欠账清零

`models/comm/ofdm` 升到 1.4.1（镜像方向修正拷入）后，用**治理资产**重新推导期望
向量并复跑 `tb_fft64_cosim`：**2560 点 0 失配**，G-B-03 通过。

**RTL、向量、期望值一个字节都没改。** 重新推导出的期望与 0.1.0 提交的内容逐字节
相同（DELTA 0.0 LSB）——此前的欠账是**出处不合规**（向量出自暂存副本），不是数值
有误。这也说明暂存的修正版镜像与治理资产 1.4.1 是同一份代码。

治理镜像自身的三判据（拷入后实跑）：

- [A] 反向对已认证 `rtl_mirror_tx`：0 失配
- [B] 末级移位前峰值 40.710，s21 的 ±64 覆盖（s20 的 ±32 不够）
- [C] 正向对浮点 `fft_chain`：最大误差 **3.5 LSB**（信号幅度 17800 LSB）

判据 C 修正前是 46725 LSB。另做一次独立复核：镜像输出 vs `fft(x)/8` 最大 3.3 LSB。

五个 TB 全绿：cosim / sdf_core / direction / reorder / 顶层。

**过程中的一次误判**（已记入 `docs/limitations.md` §3）：重生成向量时按 `cp_remove`
的 `{im, re}` 字序写，而本包 TB 用 `{re, im}`。交换 re/im 等价于 `z → j·conj(z)`，
失配模式与频点反转 `X[k] → X[-k]` 几乎一样，连 bin0/bin32 仍匹配这个细节都对得上，
一度被判成 RTL 方向缺陷。拆穿它的是"两边都跟浮点 FFT 比"这一步独立判据——治理镜像
差 3.3 LSB、旧期望差 25410 LSB，而信号幅度只有 12705 LSB。TB 头注释已加字序说明。

## [0.1.1] — 2026-08-04 综合取证

OOC 综合（`xc7k325tffg900-2`，`constraints/fft64_sdf.xdc` 100 MHz）：

- WNS **+6.323 ns** @10ns（≈272 MHz），WHS **+0.158 ns**
- LUT 2251 / FF 5033 / BRAM 0 / **DSP 10**

**DSP 数与 s20 的 `ifft64_sdf` 相同**，说明内部位宽从 s20 抬到 s21 没有把复乘
挤出 DSP48E1（21×16 仍在 25×18 之内）。这一条此前只是推理，现在是实测。

资源包络按**先测量、后声明**的顺序填（实测值加余量）。G-C-01 / G-C-02 通过。

**G-B-03 仍未过**，原因不变：现有 2560 点对拍用的是暂存中已验证的修正版镜像，
不是治理资产。待修正包拷入 `models/comm/ofdm` 后复跑。（已在 0.1.2 清掉。）

## [0.1.0] — 2026-08-03 首次入库（intake）

M1 关键路径首件。需求门禁六维齐备（记录见 `var/gates/requirements-gate.json`
的 history），golden 与定点镜像先行，RTL 后写。

**结构**：R2²SDF，6 级反馈延迟 32/16/8/4/2/1，完整复乘 2 个。三个 RTL 文件：
核（恒位反序 + 侧带透传）、重排（位反序→自然序乒乓）、顶层（纯接线）。

**四项裁定落地**（owner 2026-08-03）：

- 方向与输出序均参数化，一个包两配置，只有一条证据链
- 重排放在包内（`P_NATURAL_OUT`），不另立 CBB——扇出前必须已是自然序，而
  channel_est_top 已认证、按自然序流式吃且无索引口
- frame_start 侧带由本模块透传，不用独立 delay_line——延迟天然匹配，不依赖
  任何人手算拍数
- 内部位宽 s21 而非沿用 s20

**s21 的依据是实测不是保守**：按 64 个输出 bin 逐个做对抗构造搜索，最坏 40.71
超出 s20 的 ±32（回绕，非饱和）；可证上界 45.25 也在 s21 的 ±64 之内，裕量
1.41×。真实 OFDM 信号峰值仅 3.6~4.7，随机满幅顶点 400 次最大 17.10——风险来自
结构化信号（如满幅 CW 干扰），不是典型工况。

**验证**：五个 TB 全绿，其中 `tb_fft64_cosim` 对 golden 定点镜像 **2560 样点
0 失配**（与 ofdm_tx_top 认证时同量级，门禁下限 2048）。

**三处在验证中被抓出的问题**（均已修正，过程记在 `docs/limitations.md`）：

- 侧带延迟不能从 golden 镜像推导。镜像里的 `63+3+3=69` 是**数值对应关系**不是
  时钟拍数；按拍数推的 76 也偏一拍。最终改为直接断言契约本身（`o_sb` 为高时
  `o_idx` 必须为 0），一次定位到 75。
- 顶层最初用组合三目生成 `o_idx`，违反输出寄存红线。改为下沉到 reorder（它本就
  有读地址计数器），顶层退回纯接líne。
- 核文件 319 行超出 G-A-04 的 300 行上限，旋转因子表抽成 `fft64_twiddle.svh`。
  抽出后复跑 cosim 仍 0 失配。

**已知欠账**：bit-true 证据当前用的是暂存中已验证的修正版镜像，而非
`models/comm/ofdm` 内的治理资产（后者尚有方向缺陷：只翻旋转因子表、漏翻 BF2II
的平凡 ±j，修正包已验证待拷入）。作为 G-B-03 证据前必须用治理资产复跑。

**本版未做**：综合取证、复位/CDC 证据、边界/压力/回归四子结果、签字。
（综合取证已在 0.1.1 补齐。）
