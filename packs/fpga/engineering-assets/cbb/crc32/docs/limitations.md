# crc32 — 已知限制（1.0.0）

以下各条来自实测与语义约定，非推测；验证证据见
`engineering-assets/evidence/crc32/1.0.0/`。

1. **语义是 IEEE 802.3 反射式，不是"通用 CRC-32"**：
   `init = 0xFFFFFFFF`，LSB-first 反射多项式 `0xEDB88320`，末尾按位取反。
   与非反射 MSB-first 变体（poly `0x04C11DB7` 左移、无末尾取反）**结果完全不同**。
   接线前用标准检验值确认对方语义：本模块对 `'123456789'` 输出 **0xCBF43926**。

2. **与旧模板不兼容（breaking）**：改写自
   `skills/hdl-coding/templates/internet/crc32.v` v1.0.0。原件声称"以太网帧校验"
   却实现了非反射 MSB-first 且无末尾取反，对 `'123456789'` 得 `0x0376E6E7`，
   按声称场景使用必然校验失败；另无 `i_last` 帧界、无 `o_valid` 完成指示。
   缺陷逐条记录在 RTL 模块头。

3. **无反压接口**：只有 `i_valid`，没有 `tready`。上游必须能接受"本模块无条件
   吸收"这一契约；需要背压的集成方在**上游**例化已认证的 `axis_skid_buffer`。
   G-C-05 的 backpressure 子结果按「同一帧分别以满流与 60% 气泡供流，结果逐位
   相同」这一等价判据取证 —— 证明计算只依赖被采纳的字节序列、与供流节奏无关。

4. **吞吐与时序契约**：单字节/拍，不支持多字节并行。`i_last` 拍后 **2 拍**
   `o_valid` 出单拍脉冲，`o_crc` 同拍有效并保持到下一帧。帧尾状态自动回 init，
   支持背靠背帧（`i_last` 后下一拍即可开新帧）。

5. **帧长验证边界**：实测覆盖 1..1500 字节（含以太网 MTU）与 1..256 字节的
   200 帧浸泡。更长帧未逐一验证（算法上无长度限制，但未取证）。
   **空帧（0 字节）无定义** —— `i_last` 必须伴随至少一个有效字节。

6. **不含 FCS 校验方向的判定**：本模块只**计算** FCS，不做"收端校验余数是否为
   魔数 0xC704DD7B"这类判定；接收侧校验需由使用方自行实现。

7. **综合口径**：WNS/资源来自 **OOC 综合**（`xc7k325tffg900-2`，仅
   `create_clock`），未做布局布线与 I/O 绑定。目标 200 MHz 实测达成 535 MHz，
   关键路径是单拍内 8 步反射展开的异或树。

8. **工具链**：本版全部仿真证据由 **Vivado xsim 2023.1** 产出（本机 ModelSim
   回环 RPC 故障）；`vlog` 编译不受影响，门禁 G-A-00 仍由 ModelSim 判读。
