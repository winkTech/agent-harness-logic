# Doc Gen — 文档协作生成

## 三阶段流程总览

```
Phase 1: 背景收集 — 了解受众、目标、现有材料
    ↓
Phase 2: 逐段撰写 — 澄清→脑暴→筛选→草稿→迭代
    ↓
Phase 3: 读者验证 — 用全新 Claude 测试文档盲点
```

**默认建议用户走三阶段流程**。如果用户拒绝（"直接写"），则进入自由模式。

---

## Phase 1：背景收集

### 1.1 元背景确认

先问用户 3-5 个问题：
1. 文档类型是什么？（设计文档 / API 文档 / 架构文档 / 用户手册 / README / 评审报告）
2. 主要读者是谁？（工程师 / 管理者 / 客户 / 团队内部）
3. 希望读者阅读后做什么或知道什么？
4. 有模板或格式要求吗？
5. 有什么约束？（页数、时间、保密）

### 1.2 信息倾泻

鼓励用户**不要整理，一股脑倒出来**。可以：
- 直接说（想到哪说到哪）
- 贴链接（需求文档、会议纪要、Slack 讨论）
- 指代码（"看 src/tx/scrambler.sv 的架构"）

用 `Glob`/`Grep`/`Read` 自主获取代码上下文。

### 1.3 澄清追问

用户倾泻完后，出 5-10 个澄清问题。用户可以简写回答（"1: 对, 2: 见#channel, 3: 不因为兼容"）。

**退出条件**：能问出 edge case 和 trade-off 问题而不需要再解释基础概念。

---

## Phase 2：逐段撰写

### 2.1 确定结构

根据文档类型，提供推荐结构（见下方 §文档类型模板），用户确认或调整。

### 2.2 逐段流程（每段走完再进下一段）

```
Step 1: 澄清 — 问 3-8 个关于本段该写什么的问题
Step 2: 脑暴 — 列出 5-15 个可纳入的要点
Step 3: 筛选 — 用户说"保留 1,4,7,9"之类的编号
Step 4: 缺漏检查 — "这段还有什么重要东西没覆盖？"
Step 5: 草稿 — 写入文档
Step 6: 迭代 — 用户提反馈，用 Edit 精准修改
```

> **原则**：让用户提反馈而不是自己改文档。这能学习用户的风格偏好。

每段完成后问："下一段开始？"

### 2.3 最终通读

接近完成时（80%+ 段落写完），通读全文检查：
- 跨段流畅性和一致性
- 冗余或矛盾
- 空洞的套话
- 每句话是否都有分量

---

## Phase 3：读者验证

### 3.1 预测读者问题

出 5-10 个读者会问的真实问题。

### 3.2 子代理测试

如果可用子代理：每个问题启动一个**全新 Claude**（无本对话上下文），只给文档内容和问题，看能否正确回答。

记录 Reader Claude 答对/答错的内容。

### 3.3 模糊性检查

让子代理额外检查：
- 文档中有歧义或不清楚的地方
- 文档假设读者已知道哪些知识
- 内部矛盾或前后不一致

### 3.4 修复循环

发现问题 → 回到 Phase 2 修复 → 重新测试。

**退出条件**：Reader Claude 连续正确回答所有问题，且不发现新问题。

## § 文档类型模板

### 设计文档 (Design Doc)

```
# <模块名> 设计文档
## 1. 概述
- 模块功能、设计目标、适用范围

## 2. 接口定义
- 端口列表（信号名、位宽、方向、描述）
- 协议时序图（Mermaid）

## 3. 微架构
- 模块内部框图
- 流水线阶段划分
- FSM 状态图
- 数据通路描述

## 4. 算法说明
- 算法原理
- 定点量化方案（位宽、舍入、饱和）
- Golden Model 对齐说明

## 5. 配置与寄存器
- 寄存器地址映射
- 配置参数说明

## 6. 性能分析
- 吞吐量/延迟
- 资源预估（LUT/FF/BRAM/DSP）
- 时序约束说明

## 7. 验证方案
- 测试用例列表
- 仿真通过标准
- Coverage 目标
```

### API 文档

```
# <接口名> API 参考
## 概述
## 接口定义（请求/响应格式）
## 示例
## 错误码说明
## 使用注意
```

### 架构文档

```
# <系统名> 架构
## 系统总览与设计目标
## 模块划分与层次结构
## 数据流与关键路径
## 接口协议
## 时钟/复位/电源域
## 技术选型与权衡
```

### README

```
# <项目名>
## 简介
## 快速开始（环境搭建 + 最小示例）
## 目录结构
## API/使用说明
## 架构概览
## 贡献指南
## 许可证
```

### 评审报告

```
# <审查对象> 审查报告
## 审查范围与方法
## 发现汇总（按严重级别）
## 详细发现（每个含：位置/描述/影响/建议）
## 改进建议优先级
## 附录
```

## § 铁律

1. **不读来源不写断言** — 文档中的每个技术声明必须来自已读取的代码/文档
2. **先确认大纲再写正文** — 未确认结构不进入逐段撰写
3. **每段迭代不超过 3 轮** — 3 轮无明显修改就进下一段
4. **Verilog 代码示例必须 lint 通过** — 文档中的代码块不是伪代码
5. **读者测试不可跳过** — 不验证的文档不交付

## § 反模式

| 反模式 | 正确做法 |
|:-------|:---------|
| 文档与代码脱节 | 从代码注释/接口定义自动生成 |
| 无示例无教程 | 每个 API/功能配可运行示例 |
| 跳过故障排查 | 为常见错误写调试指南 |
| 一次性输出全文 | 逐段确认，避免大段重写 |
| 假设读者已知上下文 | 明确标注前置知识要求 |
