# CHANGELOG — sb_align

## [0.1.0] — 2026-08-04 首次入库（intake）

M1 链路最后一个已知开口。需求门禁六维齐备（记录见 `var/gates/requirements-gate.json`），
事实全部来自实测。

**问题**：`fft64_sdf` 的 `o_sb` 与本符号首个输出**同拍**，而 `channel_est_top` 要求
`i_frame_start` **领先** ≥1 拍。两个已认证模块的时序契约互相冲突，且都是明文。

直连**不会报错**。同一激励下实测：H 输出点数同为 384，但 **372/384 点数值不同**——
点数正常、值全错，是最难发现的一类失效。

根因（`channel_est_top.sv:50-53`）：`r_fs_pend` 由 `i_frame_start` 在本拍末置起，
而 `ri_fs_take` 用的是当拍旧值；同拍到达时 LTS1[0] 不被标记，标记落到下一个样点，
整个 LTS 窗错一位。

**为什么新起一件而不是改两边**（owner 裁定）：两边的时序各自都是明文且已签字的
契约，冲突在它们**之间**——就在它们之间解。改 `fft64` 的 `o_sb` 要动它的输出契约
和两个 TB 的断言；改 `channel_est_top` 要动链路里最复杂的那个模块（CORDIC + CPE 链）
的输入契约与内部时序，回归面最大。

**做法**：小深度 FIFO + "先报后送"。带 `sb` 的样点轮到发送时先出一个
`tvalid=0` 且 `o_frame_start=1` 的气泡拍，下一拍再送它——frame_start 恰好领先 1 拍，
且那一拍没有别的样点被接受（否则标记会落到错的样点上）。

**验证**：

- `tb_sb_align` — 侧带领先 / 数据透传 / 瞬态反压 / 溢出可见且粘滞 / 复位，5 项全过
- `tb/integration/tb_ce_aligned` — **接真实 `channel_est_top`，372/384 的差异归零**，
  且未溢出。这是本件存在意义的直接判据：同一套激励、同一个参考，只把 frame_start
  的时机换成"经 sb_align"。

**一处写 TB 时被自己纠正的判据**：T3 初版要求"任意反压下不丢数据"，实测 226/256 ——
但那是我要求了模块结构上给不了的东西：上游不可停顿，持续反压下任何有限深度都会
溢出。改为测它**能**提供的性质（瞬态积压 ≤ 深度余量时逐点一致），超出部分由 T4 的
溢出可见性兜底，并把这条结构性事实写进 `docs/limitations.md` §1。

**输出全部寄存**：RL-OUT 门禁只查 "assign 输出 ← `always_comb`" 这一条路径，本模块
不用 `always_comb`，即便组合直出也能过门——但那是钻检查器的空子，按红线本意做了寄存。

**未做**：综合取证、复位/CDC 证据、边界/压力/回归四子结果、第二仿真器交叉验证、签字。
