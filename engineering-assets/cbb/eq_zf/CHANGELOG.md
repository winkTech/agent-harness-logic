## 1.1.1 — 2026-08-09（harness 修复，RTL 与判卷结果一字未改）

**RTL / 向量 / 判卷数字全部不变**，改的只有 `run_sim.cjs`。owner 2026-08-09 批准按
patch 处理、不重新签字；1.1.0 的 signoff 记录原样保留。

### `--install` 会把"没跑起来"当成合法结果落盘

任一 suite 的 `judgements === 0` 即拒绝落盘、退出码 2（与真实失败的 1 区分），并打印
该 suite 的真实工具输出。

`judgements === 0` 意味着这个 suite 一行判据都没产出——iverilog/xelab 失败、向量路径
错之类的**工具链故障**，不是一个合法的判定结果。照旧带 `pass:false` 落盘的话，它会
覆盖掉已封存的好证据，而证据文件里"工具坏了"与"RTL 回归了"长得一模一样：前者该修
工具，后者该查 RTL。

不是新规矩——库内 `cp_remove` / `fft64_sdf` / `sb_align` 三件本来就这么做
（`!registers.length` / `!stab[k]` 即退出）。本件与 `mod_demapper` 是仅有的两个
collect-then-write 的包，都漏了这条，一并补齐。

**发现路径**：给 `mod_demapper` 做 xsim 交叉验证时，`--xsim` 因 Windows 批处理包装器
吞掉 `-testplusarg` 的 `=` 而整档没跑起来，却被记成 `pass:false`。本件不用 plusarg，
不受那个缺陷影响，但**落盘语义的洞是同一个**。

### 实测

守卫经过实证会触发：临时移走 `tb/tb_eq_recip.sv` 使其编译失败，`--install` 如实报出
"未产出任何判据行，判定为**未跑起来**"、打印 iverilog 真实报错、拒绝落盘；已封存证据
未被改动（复验仍 `pass=true / 4370`）。正常路径不误触发（四个 TB 全 PASS，摘要照常）。

## 0.1.0 — 2026-08-05

首版。ZF 频域均衡 + 64→48 数据子载波提取与排序。

### 立件依据

算法三项由 owner 2026-08-04 裁定，因为知识库对本件是**真空的**：
`algorithm_spec.md` 对"均衡"只有框图里一个方块，`rx_chain` 建的是理想信道链、没有
均衡级，`models/comm/channel_est` 只有 `generate_vectors.m`。

| 裁定 | 取 | 弃 | 理由 |
|---|---|---|---|
| ① 算法 | ZF | MMSE | MMSE 要噪声方差，而 `channel_est_top` 只产出 H |
| ② 除法 | 共轭乘 + 实数倒数 | 复数除法 / 复用 CORDIC | 流水规整、资源可预估 |
| ③ 载波提取 | 在件内 | 交给下游 | 导频/DC/保护带的 H 本就不该被使用 |
| ④ 除零 | 置零 + erasure | 饱和 / 旁路 | 满量程会被软解调器读成"高置信度的某个星座点"，对译码器的伤害比擦除大得多 |

### 进 RTL 前的四项实测收敛

| 项 | 结论 | 依据 |
|---|---|---|
| 倒数精度 | 8 位表 + 一次 Newton | 实现误差 7.33e-05，受 r1 的 Q2.14 位宽地板支配（3.05e-05~6.10e-05）而非算法 |
| 输出格式 | Q4.12 + 显式饱和 | SNR=20 饱和率 0.0117%，SNR=30 为 0 |
| Y 路深度 | ≥158，取 256 | `tb_y_depth` 在真实链路实测；最小帧间距 158，帧间距充分 109 |
| 除零行为 | 置零 + erasure，只判精确零 | 460800 样本中精确零一次未出现，但结构上可能，RTL 必须全定义 |

`channel_est_top` 模块头那句"约 110 拍"经核对是对的，但**含义不同**：实测"末个 Y 拍
→ 首个 H 拍"= 46 拍，H 输出本身占 64 拍，46+64=110——文档说的是"输出**完成**"，而
Y 缓冲要的是"输出**开始**"。照抄它去定深度会漏掉最小帧间距那 158 拍。

### 实测

- **位真 2304 点 0 容差**（≥ G-B-03 的 2048 门限），对 `rtl_mirror_eq` 导出的期望值；
  iverilog 与 Vivado xsim 2023.1 各自复跑
- OOC 综合（xc7k325tffg900-2）：WNS **+3.861 ns** @10ns（≈163 MHz），WHS +0.100 ns，
  **0 失败端点**；LUT 872 / FF 290 / BRAM 1.5 / DSP 12，全在包络内
- `vlog` 编译 **0 错 0 警**

### 开发过程中实测抓出的缺陷（全部已修）

1. **`P_YDEPTH` 取了 192 而非 2 的幂** —— `$clog2(192)=8`，指针实际回绕于 256，
   地址 192..255 越界。症状极典型：前 192 点全对，第 193 点起吐 `xxxxxxxx`。
2. **判卷向量的行序与硬件不一致** —— 定位靠 erasure 位置：期望在符号内偏移 0/7/14…，
   实测在 4/11/18…，而那 7 个载波的 bin 在升序里的位置恰好就是 4/11/18/24/31/38/45，
   完全吻合，于是确认 RTL 对、向量错。后续查明 golden 序才是系统契约，改为在件内重排。
3. **TB 的 Y 激励不真实** —— 逐拍连推没留 CP 空窗，比现实苛刻得多，任何持续反压都
   必然撑爆 FIFO。那测的是激励不是 DUT。改为按 64+16 占空驱动。
4. **倒数误差判据的界取错** —— 用了分析报告里的算法误差 3.8e-06，而 RTL 里 r1 是
   Q2.14 的 16 位数，自身 1 LSB 就是 3e-05~6e-05 的相对分辨率。是 RTL 实测反查出
   分析的口径问题，报告已回头修正。

### 已知边界

下游平均接受率必须 ≥ 80%（Y 的占空 64/80）。低于此值 Y 只能堆积，加深 FIFO 只是
推迟不是解决。此工况下拉起 `o_y_overflow` 而非静默丢点——**集成方必须接出去看**。
