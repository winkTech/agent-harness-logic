## 0. 口径、时效与数据可信度声明

**平台边界**：本报告以本机 `~/.claude` 实例（agent-harness-logic 仓库及其运行时目录）为分析对象。该实例为单操作者环境，`projects/` 下无多账号维度数据，因此**用户规模只能按"1 名操作者 × 多 transport"计**，团队级结论不可验证，另有定性判断单独标注（见 §2.7）。

**观测窗口**：会话计量覆盖 2026-08-02 ~ 2026-09-06（16 个活跃日）；hook 延迟覆盖 2026-07-29 ~ 2026-09-04（21 个有数据日）；交付与评审指标为 `weekly-report.json` 生成的 30 天窗口（生成于 2026-07-28）。**数据截至 2026-09-06，距今约 2 个月，本报告不外推至 09-07 之后**；所有"趋势"判断限于窗口内。

**单价的处理**：`var/metrics/costs.jsonl` 仅 1 条记录且四类 token 全为 0，**平台没有产生任何真实账单数据**。因此 §1.4 的金额为**折算值**：token 量为实测，单价为假设参数（顶配档 15/75 美元每百万 token，缓存写 1.25×，缓存读 0.1×）。§1.4 同时给出 ±50% 敏感度区间。若实际采用订阅制而非按量计费，金额应读作"等价按量成本"，其意义转为配额消耗量而非现金支出。

**样本排除**：`projects/` 下 110 个文件中 46 个为 `subagents/` 子代理轨迹，13 个为验收夹具（无 usage 字段）；token 汇总仅统计带 `message.usage` 的记录（55,146 条总记录中 17,418 条为带计量的 assistant 消息），不存在重复计数。

### 1.2 使用情况

**活跃度**：观测窗 36 天内有 16 天产生计量消息（44.4%），呈"高强度冲刺 + 长间歇"形态——8 月上旬连续 3 天（08-03~05，日增 1,185~2,667 条）与中旬连续 3 天（08-14~16，日增 1,991~3,504 条）为两个高峰，9 月仅 3 天有活动。这是单人项目节奏，不是平台可用性问题，但意味着**任何按"日均"摊薄的成本指标都会失真**（16 日口径 vs 38 日口径相差 2.4 倍：$1,050/日 vs $442/日）。

**功能模块使用频率**（10,349 次工具调用，占比为全窗合计）：

|---|---|---|---|

| Edit | 1,960 | 18.9% | 增量修改 |

### 1.4 成本结构

按假设单价折算（16 个活跃日）：

| 模型 | prompt 侧 token | 折合 USD | 占比 |
|---|---|---|---|
| claude-opus-5 | 5,955,230,953 | 15,239.4 | 90.70% |
| claude-fable-5 | 382,320,823 | 1,291.6 | 7.69% |
| claude-fable-5-1 | 91,740,674 | 244.5 | 1.46% |
| claude-sonnet-5 | 7,282,120 | 21.4 | 0.13% |
| claude-haiku-4-5 | 1,410,912 | 4.6 | 0.03% |
| **合计** | **6,437,985,482** | **16,801.4** | 100% |

**成本项结构（比金额更重要）**：

| 成本项 | USD | 占比 |
|---|---|---|
| cache_read | 9,131.9 | **54.35%** |
| cache_creation | 6,560.6 | **39.05%** |
| output | 1,106.8 | 6.59% |
| input | 3.0 | 0.01% |

三点判读：

1. **93.4% 的支出发生在缓存上**（读 + 写），与"模型输出贵"的直觉相反。output 单价是缓存读的 50 倍，但因量只有 0.23%，绝对额仅 6.6%。
2. **cache_read 单价虽为 0.1×，却因量占 94.56% 成为第一大成本项（54.35%）**。这意味着"提高命中率"不是降本手段——命中率已在 94.6%，再提升空间有限；真正的杠杆是**减少被缓存的 prompt 总量**与**减少缓存写入次数**。
3. **cache_creation 的 39% 是低效信号**：写入按 1.25× 计价，仅 5.43% 的量就吃掉近四成预算。每一次前缀重建（规则文件改动、工具清单重排、系统提示变动）都会让后续所有会话重新付这笔钱。

**聚合单价**：$2.61 / 百万 prompt token（blended）。**敏感度**：单价 ±50% → 总额区间 **$8,401 ~ $25,202**；日均（16 活跃日）$525 ~ $1,575。金额绝对值请按此区间理解，**结构性占比（54/39/7）对单价不敏感，可独立采信**。

## 2. 关键发现

### 2.1 F1｜成本结构失衡：缓存写入费率偏高（定级：成本浪费）

**证据**：cache_creation 占 prompt 量 5.43%，占金额 39.05%；平均每 assistant 消息写入 **20,088 token**。对比业界常见区间（长会话中缓存写入占 prompt 量 2%~4%），当前值高出约 35%~170%。

**归因（三项，按可能性排序）**：
1. 规则/系统提示类文件（`CLAUDE.md`、`AGENTS.md`、`docs/rules/*`、skill 清单）在观测窗内多次变更，每次变更使全部活跃会话的前缀缓存失效；
2. 工具清单与 skill 列表顺序不稳定（`skills/` 28 项、hook 16 条），前端排序变动即触发重写；
3. 8 月中旬的高强度期（08-16 单日 3,504 条消息、1.33 亿 prompt token）叠加频繁的子代理派生（46 个子代理轨迹文件），子代理各自建立独立前缀。

**影响**：若把写入率从 5.43% 降到 4.3%，按当前单价可省 **$980 ~ $1,640/窗口**（占总额 5.8%~9.8%）。该项为**低风险高确定性**收益。

### 2.2 F2｜负载极度集中：两个会话决定 93.9% 的成本（定级：优化）

**证据**：

| 会话 | 消息数 | output | cache_write | cache_read | prompt 占比 |
|---|---|---|---|---|---|
| `a2fc43bd…` | 7,172 | 8,886,120 | 139,846,351 | 3,264,500,746 | **52.9%** |
| `66e3b093…` | 7,914 | 4,740,638 | 191,633,359 | 2,447,996,152 | **41.0%** |
| `951e378b…` | 1,596 | 623,134 | 7,199,094 | 191,221,194 | 3.1% |
| `c7b89091…` | 695 | 477,521 | 10,581,673 | 182,883,053 | 3.0% |
| 其余 5 个 | 41 | 30,698 | 610,857 | 1,357,679 | <0.01% |

**判读**：前两会话各 7,000+ 条消息，单会话 prompt 达 32.6 亿 / 24.5 亿 token。这既是成本集中点，也是**唯一值得优化的地方**——但要注意反向风险：这两个会话之所以缓存效率高（命中率 94%+），正因为上下文连续。**切碎会话会降低单次成本却抬高写入率**，两者存在对冲（详见 §3 R3 的权衡说明与验证前置条件）。

### 2.3 F3｜延迟预算达标，但长尾失控（定级：风险）

**证据**：p95 达标（80/110 ms），但：
- 2026-08-01 单日出现成对极值 **5,576 ms / 5,578 ms**（preflight/postflight 同日、几乎同值），形态指向**一次同步 I/O 或锁竞争阻塞**，而非普遍性劣化；
- 2026-08-05 p95 达 **150 / 155 ms**，已占用预算 75% / 62%，为窗口内最差日；
- 日均阻塞在 1.2 s ~ 222.9 s 之间波动，08-16 峰值 222,959 ms（3.7 分钟）对应 5,172 次判定。

**判读**：聚合视角下 19.3 分钟/21 天完全可接受（0.92 分钟/日），**均值掩盖了问题**。真正的风险是"单次操作被打断 5 秒以上"——这在交互式工作流中直接破坏体感，且当前无超时兜底。另需注意 08-14 起 preflight p95 从 103~150 ms 回落到 26~97 ms，同时判定量增长 3 倍（2,979 次/日），说明期间存在一次有效的性能改进，**该改进的实施记录未进入任何指标文件，属可复现性缺口**。

### 2.4 F4｜评估层（V）观测断裂，指标不可采信（定级：阻断）

这是本报告最重要的发现：**平台在测量的东西，与其声称测量的东西不一致**。

| 指标 | 报告值 | 实际问题 |
|---|---|---|
| 交付成功率 | 71.58%（1,000 事件） | `partial` 占 **539 件（53.9%）**，pass 仅 330（33.0%），fail 131（13.1%）。partial 过半意味着"成功"判定主要来自非明确通过 |
| 重试次数 | **0** | 1,000 个事件重试恒为 0，与 3.08:1 的 Bash 执行/修改比矛盾（高频执行必然伴随重跑）。**retries 未埋点**，不是真的没有重试 |
| 误拦率 | 0.0%（准确率 100%） | 样本 **n=2**。二项分布下 2/2 成功的 95% 置信下界约 **22%**，无法支撑"100% 准确" |
| 风险事件 | 82 条 | 仅覆盖 **3 天**（09-02/03/04），占观测窗 7.9%。其中 `upgrade` 65 条（79.3%）、`failure` 17 条；R2 44 / R3 22 / R1 12 / R0 4 |
| Guard 覆盖 | 12/12 类，51 用例，100% | 覆盖度真实，但用例密度低（平均 4.25 例/类） |

**判读**：这不是"指标不好看"，而是**度量系统本身失效**。在 V 层不可信的前提下，§3 所有优化的 ROI 都无法被验证——这使 F4 从"一个发现"升级为"所有其他措施的前置条件"。风险事件中 79.3% 是权限升级请求且 80.5% 落在 R2/R3，说明拦截器在设计意图上是工作的，但采样窗口过短（3 天）不足以判断趋势。

### 2.5 F5｜磁盘与交付卫生：72.5% 的空间存放非运行必需资料（定级：成本浪费）

**证据**：`packs/fpga/references/` 合计 **972.8 MB / 3,029 文件**，占全仓体积 72.5%、全仓文件数（11,834）的 25.6%。但内部是**两个性质不同的问题**：

| 子目录 | 文件数 | 体积 | 平均单文件 | 性质 |
|---|---|---|---|---|
| `datasheets/` | **37** | **899.8 MB** | 24.3 MB | 技术书籍 PDF，纯参考资料，运行时不加载 |
| `vendor/` | **2,992** | 73.0 MB | 24 KB | 第三方源码（async_fifo / picorv32 / verilog-pcie 等），带 `_provenance` 来源标注 |

datasheets 前 10 个文件占该目录 86.9%（最大 183.9 MB，文件名含中文、空格与方括号，如 `软件无线电原理与应用 [楼才义，徐建良，杨小牛 编著] 2014年版.pdf`）。

**连带影响（两类，可测）**：
1. **体积 → 备份与传输**：899.8 MB 非运行资产无异地副本（`backups/` 仅 0.4 MB）。既占空间又无保护，是"体积大而无冗余"的最差组合。
2. **文件数 → git 操作放大**：2,992 个 vendor 文件是逐文件检查型钩子的主要开销来源；按仓库既有记录 0.53 s/文件的量级估算，全量体检一次约 **26 分钟**（量级推断，非本报告实测）。此前"2,892 文件提交耗时 34 分钟"的记录与本目录规模高度吻合，但**未验证具体提交包含哪些文件**，此处仅作关联提示。
3. **路径可移植性**：中文 + 空格 + 方括号的 PDF 名在 Windows/POSIX 双端打包与校验链路中反复触发转义问题。

**说明**：vendor 目录保留 `_provenance`，来源治理是到位的，因此不作为合规缺陷计入；问题仅在于它以"包内可分发单元"的形式存放了 2,992 个文件。

### 2.6 F6｜模型档位未分派，顶配承担全部负载（定级：成本浪费）

**证据**：opus-5 承载 92.5% 的 prompt token 与 90.7% 的成本；`claude-haiku-4-5` 仅 0.03%，`sonnet-5` 0.13%。而 10,349 次工具调用中，Bash/Read/Grep/Glob 类"读取与执行"占 69.8%——这类步骤的输出理解与格式整理属窄决策，无需顶配模型。

**判读**：当前不存在任务-模型分派表，也没有级联升级机制（全部直达顶配）。这是最典型的"用大炮打蚊子"型资源错配，且**不需要改动架构即可试点**。

### 2.7 F7｜用户规模维度不可量化（定级：未知区，非缺陷）

单机实例只有 1 名操作者、9 个有计量会话，**无法产出"用户规模"指标**。定性判断（标注为不可验证）：平台通过 pack 分发（`packs/fpga`、`packs/office`）与多 transport 适配（Claude Code / WorkBuddy / Codex）设计为可外部复用，但仓库内无安装量、活跃用户数、按人用量分层的任何记录。若要回答"用户规模"问题，需引入外部账号体系或使用回传，当前架构**不具备该能力**，这是设计层面的观测缺口而非数据缺失。

| C 上下文管理 | 命中率 94.56%，写入率 5.43%，单消息写入 20,088 token | `PreCompact` hook 存在但无触发统计；无压缩策略证据 |
| S 状态存储 | `var/` 65.1 MB + `engineering-assets/var/` 121.6 MB；semantic-index 8.6 MB；state-dir 迁移分支进行中 | 状态与代码同仓，仍受"仓库整包替换"连坐风险 |
| L 生命周期/安全 | 8 事件 / 16 hook；bash-safety-guard 12 类全覆盖；risk-events 82 条（升级占 79.3%） | 无 hook 级超时兜底（max 5.58 s） |

| 范式 P | 单机单进程 + hook 注入 + pack 分发；多 transport schema 适配 | 无多用户/多租户观测能力 |

## 3. 降本增效建议

每项给出：措施、依据、预期收益（量化或定性）、实施成本、风险与回滚。

### R1｜前缀稳定化与缓存写入削减（C 层）

**措施**：
1. 把 `CLAUDE.md` / `AGENTS.md` / `docs/rules/*` / skill 清单定义为"不可变前缀"，按 `系统提示 → 工具清单 → 规则 → 用户输入` 的固定序列组装，禁止前端重排；
2. 规则类文件的变更改为**批量发布窗口**（如每周一次合并），避免日内多次改动引发全量重建；
3. 子代理复用父会话前缀片段，避免各自冷启动（46 个子代理文件是主要变量）。

**预期收益**：写入率 5.43% → 4.3%~4.6%，节省 **$980 ~ $1,640/窗口**（占总额 5.8%~9.8%）；同时降低单次操作首字节延迟。
**实施成本**：1~2 人日（组装顺序与文件分组改动，无需改架构）。
**风险/回滚**：若规则顺序调整导致 agent 行为漂移，回滚组装脚本即可；建议先在非关键项目验证 3 天。
**可信度**：高（机制明确，量级可测）。

### R2｜磁盘分层：体积与文件数分开治理（S 层）

**措施**：
1. **体积侧**：`datasheets/`（37 PDF / 899.8 MB）迁至仓库外知识库目录，pack 内只保留 `catalog/` 索引 + 按需检索入口；PDF 命名规范化为 ASCII slug，中文原名存入元数据表。
2. **文件数侧**：`vendor/`（2,992 文件 / 73.0 MB）改为 **git submodule 或版本化 tarball**，工作区可展开、包分发不携带；`_provenance` 迁移为 submodule 指针记录。
3. 迁移前 grep 全量相对路径引用；迁移后跑 `sync-pack-skills --check` 确认无漂移。

**预期收益**（可测，非金额）：
- **体积**：1,342.7 MB → **442.9 MB（-67.0%）**；若仅移 PDF 不压缩 vendor，已得主要收益。
- **文件数**：11,834 → 8,842（**-25.3%**）；按 0.53 s/文件量级估算，逐文件体检型提交可省 **~26 分钟/次**。
- **备份**：非运行资产移出后，仓内资产首次具备"可全量备份"的体量（<450 MB）。
- 消除中文+空格+方括号路径的跨端转义风险。
**实施成本**：2~3 人日（含索引重建、引用核查、submodule 接入）。
**风险/回滚**：技能内若有硬编码相对路径会断链——迁移前必须先 grep 全量引用；回滚点为原目录 rename 保留 30 天；submodule 方案需确认三端（Claude Code / WorkBuddy / Codex）拉取流程均支持。
**可信度**：高（体积与文件数为硬数据；时间收益为量级估算）。

### R3｜V 层度量修复（V 层）— 所有其他措施的前置条件

**措施**：
1. `retries` 埋点：在 postflight 记录"同一目标 15 分钟内重复执行"计数，区分"验证重跑"与"失败重试"；
2. `delivery` 三态归因：`partial` 必须附带"未覆盖项"字段，禁止无理由 partial；否则计为 fail；
3. FP 样本量下限：误拦率统计要求 **n ≥ 30**，低于阈值时报告"样本不足"而非"0.0%"；
4. risk-events 常开：从当前 3 天覆盖扩展到全窗；
5. 口径文档化：每个指标写明"分子/分母/采集点/已知盲区"。

**预期收益**：不直接省钱，但使 R1/R4/R5 的收益**可验证**。当前状态下，任何优化都无法证明有效——这是元收益，价值高于单项节约。
**实施成本**：2~3 人日。
**风险/回滚**：埋点本身增加 hook 开销，需控制在 p95 +5 ms 内（纳入 M4a 预算校验）。
**可信度**：高。

### R4｜Hook 长尾兜底（L 层）

**措施**：对 preflight/postflight 加**硬超时 3,000 ms + 超时降级放行 + 告警计数**；对成对极值（5,576/5,578 ms 同现）建立"单日 max > 1,000 ms 即记为事件"的采集规则。

**预期收益**：消除 5.58 s 级长尾（预算 27.9 倍），最差体感事件从"5 秒卡顿"变为"3 秒后放行"；p95 不受影响（当前 80~110 ms，余量充足）。
**实施成本**：0.5 人日（配置级）。
**风险/回滚**：超时放行会让本该拦截的操作通过——**必须限定只对非安全类 hook 生效，安全拦截类（bash-safety-guard / file-protection）不设超时放行**。
**可信度**：高。

### R5｜模型分派与降档试点（模型组合）

**措施**：建立任务-模型分派表，先覆盖三类窄任务：① 只读检索与摘要（Read/Grep/Glob 结果整理）；② 日志与报告格式归一；③ 模板填充与字段校验。三类的**升级条件**：结果含冲突、需跨文件推理、或校验失败 → 升级至顶配。降档后监控升级率，**升级率 > 20% 视为降档失败**。

**预期收益**：若 15% 的 prompt 量从顶配降至轻档（0.2× 单价），节省 **≈ $1,829/窗口（10.9%）**；保守取 10% 流量则为 **$1,220（7.3%）**。
**实施成本**：3~4 人日（分派表 + 路由改造 + 升级率监控）。
**风险/回滚**：降档导致质量下滑且不易察觉——必须先有 R3 的度量，才能判定"升级率"；回滚点为分派表开关（保持 100% 顶配的默认路径）。
**可信度**：中（收益模型清晰，实际可降档比例未验证）。

### R6｜长会话上下文策略（E 层）— 需前置验证，谨慎推进

**措施**：对超长会话（>5,000 消息）在**任务边界**处切分：写状态文件 → 新会话读摘要 → 继续。不做固定轮次强制切分。

**预期收益**：若平均上下文降低 20%，理论节省 **≈ $3,155/窗口（18.8%）**。
**实施成本**：3~5 人日。
**风险/回滚**：**这是本报告中唯一可能产生负收益的措施**。切分会破坏前缀连续性，抬高 cache_creation（39% 的成本项）。因此必须：① 先由 R3 提供可比的"写入率"基线；② 只在任务边界切分；③ A/B 观测 2 周，写入率上升超过 15% 即停止。
**可信度**：低（方向正确，量级不确定，存在对冲）。

## 4. 结论与行动计划

### 4.1 结论

1. **平台的成本问题不在"用得多"，而在"结构的三个错配"**：93.4% 支出集中于缓存、92.5% 负载集中于单一模型档、93.9% 用量集中于两个会话。三者叠加意味着**优化面极小且明确**，但也意味着**任何针对边缘路径的优化都没有意义**。
2. **平台的度量问题比成本问题更严重**。`retries` 恒 0、FP 样本 n=2、风险事件仅 3 天覆盖、`partial` 占 53.9%——当前周报给出的 71.58% 成功率不具备决策价值。修复度量必须先于任何降本动作。
3. **延迟优化已接近收益边界**。p95 达标且余量 56%~60%，继续压缩 p95 的边际收益低于处理 27.9 倍长尾的收益。
4. **磁盘是唯一"零风险立即可得"的收益**：899.8 MB 参考资料不参与运行，移出即可减 67.0% 体积；vendor 改为 submodule 再减 25.3% 文件数。代价只是引用核查。

### 4.2 分阶段实施

| 阶段 | 周期 | 动作 | 交付物 | 验收指标 |
|---|---|---|---|---|
| **阶段 0：度量与兜底** | 第 1 周 | R3（度量修复）+ R4（hook 超时） | 指标口径文档 v1；retries 埋点上线；超时降级开关 | retries 非零且可归因；max 延迟 ≤ 3,000 ms；单日 max>1,000 ms 事件有记录 |
| **阶段 1：零风险削减** | 第 2~3 周 | R1（前缀稳定化）+ R2（资料库分层） | 组装顺序规范；资料库迁移 + ASCII 命名映射表 | 写入率 ≤ 4.6%；仓体积 ≤ 500 MB；文件数 ≤ 9,000；`sync-pack-skills --check` 无漂移 |
| **阶段 2：分档试点** | 第 4~6 周 | R5（三类窄任务降档，限 15% 流量） | 任务-模型分派表 v1；升级率看板 | 升级率 ≤ 20%；质量指标不低于基线；成本降 ≥ 7% |
| **阶段 3：会话策略（条件执行）** | 第 7~9 周 | R6（仅在阶段 2 达标后启动，A/B 2 周） | 切分策略与状态文件模板；A/B 报告 | 写入率上升 ≤ 15%；净成本下降；无任务中断 |
| **阶段 4：复盘固化** | 第 10 周 | 口径入 `docs/rules`；指标纳入周报；风险事件常开 | 复盘报告；规则增补 | 全部指标可复算；无"样本不足"类占位结论 |

**进入下一阶段的硬性条件**（避免顺序失控）：
- 阶段 1 → 2：写入率基线稳定 ≥ 3 天，且度量修复后交付成功率可复算；
- 阶段 2 → 3：升级率连续 2 周 ≤ 20%，且 A/B 组成本差异显著（>5%）；
- 任一阶段写入率反弹 > 15%，回到上一阶段，不叠加新措施。

### 4.3 明确不做的事

1. **不追求更高缓存命中率**：94.56% 已接近上限，投入产出比低；重心放在"减少被缓存的量"。
2. **不压缩 output**：仅占 6.59%，压缩会直接损害质量，得不偿失。
3. **不重构六层架构**：本报告未发现阻断性架构缺陷（F4 是度量缺口，非架构缺陷），按"不为重构而重构"原则保留现状。
4. **不扩大 skill/工具注册面**：28 skills 实际装载 6 次（0.06%），当前应先收敛而非扩张。

## 附录 A｜指标定义与计算方法

- **prompt 侧 token** = input + cache_creation + cache_read，逐条 assistant 消息汇总。
- **缓存命中率** = cache_read / prompt 侧 token（94.56%）。
- **写入率** = cache_creation / prompt 侧 token（5.43%）。
- **单消息写入量** = cache_creation / 带 usage 的 assistant 消息数（17,418）。
- **p50/p95/p99** 用最近秩法（nearest-rank）在原始 `ms` 样本上取，非插值。
- **成本** = Σ(模型 token × 假设单价)，缓存写 1.25×、缓存读 0.1×；output 按 output 单价，不缓存。
- **会话集中度** = 单会话 prompt token / 全会话 prompt token。
- **仓体积** = 目标目录下所有文件 `size` 之和（含 `.git` 之外的全部工作区文件）。
