# Code Review

统一代码审查能力。根据审查目标选择模式。

---

## 模式选择

| 模式 | `args` 前缀 | 适用场景 | 审查对象 |
|:----|:-----------|:---------|:---------|
| **架构审查** | `architecture:` | 系统设计评审、组件间耦合、SOLID 原则、NFR | 架构设计 |
| **复杂度评估** | `complexity:` | 任务规划前评估工作量、确定工作流深度 | 任务描述/需求 |
| **代码质量** | `quality:` | Clean Code、命名规范、DRY、魔法数字、函数职责 | 代码实现 |
| **框架审计** | `audit:` | Hook/Agent/Skill 一致性、安全模式 SE-01/SE-02 | 框架制品 |

**默认模式**（不带前缀）：综合代码审查（架构 + 代码质量）。

---

## 模式 1：架构审查

### 执行流程

1. **收集架构上下文** — Glob 映射目录结构，识别关键组件和数据流
2. **评估设计原则** — SOLID / DRY / YAGNI / 关注点分离
3. **检查反模式** — God Class、循环依赖、Feature Envy、Shotgun Surgery
4. **评估非功能需求** — 可扩展性、可维护性、可测试性、安全、性能、可观测性
5. **生成审查报告**

### 铁律

1. 复杂/EPIC 实现开始前必须做架构审查
2. 未经文档化的单点故障不得批准
3. 架构权衡必须显式记录（隐藏的权衡是未来的技术债）
4. 循环依赖必须解决后才能批准设计

## 模式 2：复杂度评估

### 复杂度等级

| 等级 | 文件量 | 说明 |
|:----|:-----:|:-----|
| **SIMPLE** | 1-2 | 单文件修改，无架构决策 |
| **STANDARD** | 3-10 | 1-2 区域，少量集成 |
| **COMPLEX** | 10+ | 跨域变更，2+ 集成，新架构模式 |

### 评估维度

- **范围分析**: 影响多少文件/区域？
- **集成分析**: 涉及外部服务/API？
- **基础设施**: Docker/数据库/配置变更？
- **知识缺口**: 有陌生技术需要研究？
- **风险等级**: 安全性/回滚难度/破坏范围

### 评估流程

1. 加载需求 → 2. 分析复杂度指标 → 3. 多维度评估 → 4. 确定阶段数 → 5. 确定验证深度 → 6. 输出评估报告

```
SIMPLE → discovery → quick_spec → validation
STANDARD → + requirements → research → context → planning
COMPLEX → + self_critique → 全流程 8 阶段
```

## 模式 3：代码质量

### Clean Code 准则

| 准则 | 说明 |
|:----|:------|
| **常量代替魔法数字** | 所有硬编码值提取为命名常量 |
| **有意义的命名** | 变量/函数/类名揭示其用途 |
| **智能注释** | 只解释"为什么"，不说"是什么" |
| **单一职责** | 每个函数只做一件事 |
| **DRY** | 提取重复代码为可复用函数 |
| **封装** | 隐藏实现细节，暴露清晰接口 |
| **持续重构** | 让代码比你发现时更干净 |

### 铁律

1. 每次变更后代码要比之前更干净
2. 不允许魔法数字——提取为命名常量
3. 先写自文档化代码，注释只写"为什么"
4. 不允许函数做多件事——含"and"的函数名应拆分
5. 不允许过早优化——先写清晰的正确代码，profile 后优化热点

## 模式 4：框架审计

**适用**: 修改过 Hook / Agent / Skill / Workflow / Schema / 路由文件后，必须在提交前执行。

### 检查矩阵

| 范围 | 检查项 | 严重级别 |
|:----|:-------|:--------|
| **Hook (.cjs)** | 语法(node --check)、SE-02(JSON.parse注入)、SE-01(shell:true注入)、注册到 settings.json | 🔴 CRITICAL |
| **Skill (SKILL.md)** | 出现在 skill-catalog、前导元数据完整、有 Agent 引用 | 🟡 HIGH |
| **Agent (.md)** | 注册到 registry、skill 列表有效、工具列表有效 | 🟡 HIGH |
| **Schema (.json)** | 有效 JSON 语法、注册到 catalog | 🔴 CRITICAL |
| **路由文件** | routing-table 语法、CLAUDE.md 一致 | 🟠 MEDIUM |

### 铁律

1. 每个检查项必须实际执行，不能自证通过
2. 用 `git diff` 检测变更，不依赖任务元数据
3. Hook 文件中的 SE-02（原型污染）不可忽略
4. 所有检查命令必须执行并捕获输出作为证据

## 反模式

| 反模式 | 正确做法 |
|:------|:---------|
| 不加 NFR 评估就批准架构 | 始终评估性能/安全/可扩展性/可观测性 |
| 用户说"小改动"就不做复杂度评估 | 客观评估，不因用户措辞降低等级 |
| 魔法数字 + 无注释代码 | 提取常量 + 自文档化命名 |
| 跳过框架审计的"小修改" | 所有 Hook/Agent/Skill 变更都跑审计 |
| 审查通过但无证据 | 每条检查必须执行命令并捕获输出 |
